# Stella Mobili BOQ System — Integration Design Document

**Brand:** Stella Mobili (one of 7 brands under PT. Mitra Usaha Lancar Jaya / MulyaOne)
**Purpose:** Room-by-room Bill of Quantities input tool for furniture projects. PIC enters items per room, tool calculates showroom pricing. On completion, the data is saved into the project, and the sales team will then have a data to work with for their quotation for the client. The formula correlating the prices are not seen anywhere except maybe in the CRM settings somewhere.

---

## 1. Overview

The BOQ tool is currently a standalone HTML file (`StellaMobili_BOM_Tool.html`). When integrating into MulyaOne CRM, it becomes part of the **Stella Mobili PIC page** — embedded as a React component (or iframe) inside the PIC's project workspace. The exact location of this page will be determined later during integration.

### Who Uses It

| Role | What They See | Access |
|------|--------------|--------|
| PIC (Person In Charge) | Showroom Price — the price from the price list; what gets quoted from the showroom floor | Full BOQ editing |
| Sales | Selling Price (derived from BOQ total) | Read-only quotation view, generated by CRM |
| Director / Operations | Real Cost and all pricing tiers | CRM admin only |

### Pricing Tiers

The pricing formulas and multipliers are **not shown anywhere in the BOQ tool UI**. The BOQ tool works entirely with Showroom Prices as they appear in the price list — the PIC simply selects items and quantities; the tool sums them up.

The formulas that relate the tiers exist as business rules in the MulyaOne CRM platform (accessible only in CRM settings, not in the BOQ module itself):

```
Real Cost  →  × 1/0.7   →  Showroom Price  (what the price list contains; PIC uses this)
Showroom   →  × 1/0.55  →  Selling Price   (Sales team — derived by CRM, not the BOQ tool)

Max Discount: 20% + 5% tiered (NOT flat 25%)
  Example: Rp 10,000,000 → after 20% = Rp 8,000,000 → after 5% = Rp 7,600,000
  Floor: 1.974× Real Cost

These multipliers (0.7, 0.55, discount caps) are configurable in CRM settings, not hardcoded in this tool.
```

### 2.3 BOM Item (a single row in the table)

```typescript
interface BomItem {
  id: number;             // Date.now() + Math.random() — unique row identifier
  category: string;       // e.g. "Base Unit", "Wardrobe Swing Door 110", "Handles"
  subcat: string;         // Sub-category from price list (e.g. "BU 1 Door")
  desc: string;           // Item description e.g. "BU Shelf w.300"
  finish: string;         // Finish name e.g. "TZ (High Gloss & Satin)" or "(No Finish)"
  variant: string;        // "standard" | "gola" | "" (empty for wardrobe/accessories)
  thickness: string;      // "18mm", "25mm", "" (empty = unknown)
  unit: string;           // "set" | "pcs" | "m" | "m2" etc.
  w: number | null;       // Width in mm (from price list)
  h: number | null;       // Height in mm
  d: number | null;       // Depth in mm
  qty: number;            // Quantity (decimal allowed: 0.5, 1.5, etc.)
  price: number;          // Unit price in IDR (Showroom Price)
  notes: string;          // PIC's free-text note for this item
  custom: boolean;        // true = manually entered, not from price list
  altGroup: string | null; // legacy — always null on new items; makeAlt feature removed from UI
}
```

interface BoqSaveState {

### 3.2 Kitchen Items

```typescript
type KitchenCategory =
  | 'Base Unit' | 'Wall Unit' | 'Tall Unit'
  | 'Artdeco Base Unit' | 'Artdeco Wall Unit' | 'Artdeco Tall Unit'
  | 'Glass Doors' | 'Ornament Artdeco';

interface KitchenItem {
  desc: string;           // "BU Shelf w.300"
  subcat: string;         // "BU 1 Door" etc.
  unit: string;           // "set"
  w: number | null;
  h: number | null;
  d: number | null;
  thicknesses?: Record<string, string>; // finish__variant → "18mm"
  prices: Record<string, number>;
  // Price key format: "{FinishName}__{standard|gola}"
  // Examples:
  //   "TZ (High Gloss & Satin)__standard": 2721000
  //   "TZ (High Gloss & Satin)__gola":     2500000
  //   "Classic Doors PVC__standard":       1980000
  //   "(No Finish)__standard":             850000
  // NOTE: Gola key ABSENT = this item does NOT support Gola for that finish
}
```

**Critical Gola Rule:** Gola availability is per item+finish combination.
- `prices["TZ__gola"]` exists → Gola supported
- `prices["TZ__gola"]` absent → Gola NOT supported → must show error, block add
- This is validated in `validateGola(item, finish, variant)` — never bypass this

**Kitchen Categories with No Handle Selector** (variant is always blank/ignored):
`Glass Doors`, `Ornament Artdeco`, `Artdeco Base Unit`, `Artdeco Wall Unit`, `Artdeco Tall Unit`

## 5. Item Addition Flow (Business Logic)

The add-bar is the core interaction. For each section:

### Kitchen Add Flow
1. User selects **Category** → triggers `onKitCatChange()`:
   - Refreshes finish dropdown (filtered to finishes that exist in this category)
   - Hides handle selector for `NO_HANDLE_CATS`
2. User selects **Finish** → triggers `onKitFinishChange()`:
   - Updates thickness display (regex extract of `Nmm` from finish name, else empty)
   - Clears search
3. User selects **Handle** (`standard` | `gola`)
4. User **searches** for item → dropdown shows items matching the finish+variant
   - Filter: if `gola` selected, only show items that have `finish__gola` price key
   - Filter: if `standard`, only show items that have `finish__standard` price key
5. User selects item from dropdown → price preview updates
6. User sets **Qty** → press Enter or click `+ Add`
7. On add: `validateGola()` runs again as final guard
8. Row is pushed to `unit.items.kitchen[]`

### Wardrobe Add Flow
Similar to kitchen, but:
- No variant (no gola/standard split)
- Glass categories show a two-level selector (glass type + hinge/frame)
- No-finish categories skip the finish selector entirely
- Thickness is read from `item.thicknesses[finishKey]` first, then regex fallback

### Accessories Add Flow
- No finish, no variant, no thickness
- Just: Category → Search → Qty → Add

### Custom Item Flow
Any section supports a Custom button that opens a modal:
- Fields: Description, Finish/Material (free text), Thickness (free text), Unit Price, Qty, Unit, Notes
- Stored with `custom: true` — clearly labelled in the table
- Not linked to price list; price is manually entered

## 6. Key Calculations

### In the BOQ Tool (Showroom Price only)

```typescript
// Unit total (showroom price)
const unitTotal = (unit: Unit): number =>
  ['kitchen','wardrobe','accessories'].reduce((s, sec) =>
    s + unit.items[sec as keyof Unit['items']].reduce((ss, r) => ss + r.price * r.qty, 0), 0
  );

// Grand total (showroom price, excl. PPN/VAT) — this is the value saved in the revision
const grandTotal = units.reduce((s, u) => s + unitTotal(u), 0);
```

The BOQ tool only calculates and displays Showroom Prices. No selling price, no discount, no margin is computed or shown here.

### In the CRM (after BOQ is saved — not in the BOQ tool)

These calculations happen server-side in the CRM platform when the quotation is generated. The multipliers are CRM-configurable:

```typescript
// Selling price (Sales team — CRM-generated, never shown in BOQ tool)
const sellingPrice = grandTotal / SELLING_PRICE_DIVISOR;  // default: 0.55, configurable in CRM settings

// After max discount (20% + 5% tiered — configurable in CRM settings)
const afterDiscount = sellingPrice * (1 - TIER1_DISCOUNT) * (1 - TIER2_DISCOUNT); // default: 0.80 × 0.95
```

## 8. CRM Integration — API Endpoints

All endpoints are under `/api/stella/` and require authentication.

### Projects (PIC role)

```
GET    /api/stella/projects
       → List PIC's projects (or all, for admin)
       Response: { projects: StellaProject[] }

POST   /api/stella/projects
       Body: { name, client, date, notes, priceListVersion }
       Response: { project: StellaProject }

GET    /api/stella/projects/:id
       → Returns project + latest revision's units
       Response: { project, latestRevision: StellaBoqRevision }

POST   /api/stella/projects/:id/revisions
       Body: { units: Unit[], unitCounter, priceListVersion }
       → Increments revisionNumber, stores snapshot, updates grandTotal
       Response: { revision: StellaBoqRevision }

GET    /api/stella/projects/:id/revisions
       → List all revisions (for history)
       Response: { revisions: StellaBoqRevision[] }

PATCH  /api/stella/projects/:id
       Body: Partial<{ name, client, pic, date, notes, status }>
       Response: { project: StellaProject }
```

### Price Lists

```
GET    /api/stella/price-lists
       → List all available versions
       Response: { versions: string[], latest: string }

GET    /api/stella/price-lists/:version
       → Full price data for one version
       Response: PriceData
       Note: This is ~1MB. Cache aggressively (immutable per version).
```

### Quotation (auto-generated, Sales-facing)

```
POST   /api/stella/projects/:id/quotation
       → Generate or regenerate quotation from latest approved revision
       Body: { discountPct?: number, notes?: string }
       Response: { quotation: StellaQuotation }

GET    /api/stella/quotations/:id
       → Sales team view (shows sellingPrice, not showroomTotal)
       Response: { quotation: StellaQuotation, project: StellaProject }

PATCH  /api/stella/quotations/:id
       Body: { discountPct, status, notes }
       Response: { quotation: StellaQuotation }
```

### Excel / PDF Export

```
GET    /api/stella/projects/:id/export/excel
       → Server-side Excel generation (SheetJS on server)
       Response: application/vnd.openxmlformats-officedocument.spreadsheetml.sheet

GET    /api/stella/projects/:id/export/pdf
       → Puppeteer PDF generation
       Response: application/pdf
```

### State Management

The BOQ state is self-contained and complex. Recommended approach:
- Use a **Zustand store** or **React Context** for BOQ state

- Fetch `PriceData` once on mount and keep in the store (it's ~1MB, cache with SWR/React Query with long stale time)

## 11. Price List Import Pipeline

Price lists come from 3 Excel files per version:
```
Kitchen_PL_SM_{version}.xlsx
Wardrobe_PL_SM_{version}.xlsx
Accessories_PL_SM_{version}.xlsx
```

The extraction script (`docs/data/extract_price_data.py`) reads these and produces 3 JSON files in `docs/data/price_lists/`:
```
kitchen_{version}.json
wardrobe_{version}.json
accessories_{version}.json
```

`build_tool.py` then reads these and embeds them into the standalone HTML tool.

**For CRM:** Price list management lives in the **Stella Mobili PIC Settings** section of MulyaOne — not a generic admin area. The PIC (or whoever manages SM settings) uploads new price list files directly from that settings page.

Import flow (replaces build_tool.py):
1. PIC uploads the 3 Excel files from the **SM PIC Settings → Price Lists** page
2. Server runs the extraction logic (port Python script to Node.js, or call Python as subprocess)
3. Result is stored in `StellaPriceList.data` with the version string
4. `isLatest` flag is updated on the new version (and cleared on all others)
5. Existing projects that used an older version are unaffected (they reference their version)
6. All price list settings and version management are editable from within the CRM platform — nothing is hardcoded in the tool

### Future Flat-List Format

A planned single Excel with all SKUs in one flat sheet (easier for non-technical admins):

| section | category | description | finish | handle | thickness | price | unit | active | notes |
|---------|----------|-------------|--------|--------|-----------|-------|------|--------|-------|
| Kitchen | Base Unit | BU Shelf w.300 | TZ (High Gloss & Satin) | standard | 18mm | 2721000 | set | YES | |
| Kitchen | Base Unit | BU Shelf w.300 | TZ (High Gloss & Satin) | gola | 18mm | 2500000 | set | YES | |

When this format is available, replace the current 3-file extraction with a single-sheet parser. The `active=NO` rows should be stored in DB but hidden from search results.

## 12. Quotation Generation (CRM Responsibility — Not the BOQ Tool)

**The BOQ tool does not generate quotations.** Its only job is to capture structured BOM data and save it as a revision. The BOQ tool outputs a `grandTotal` and a `units` array — that is all.

The MulyaOne CRM reads that saved revision data and **automatically generates a quotation for the sales team** as a separate step, independent of the BOQ tool.

### What the BOQ Tool Produces

```typescript
// Saved to StellaBoqRevision (see Section 7)
{
  units: Unit[],         // Full itemised room/item data
  grandTotal: Decimal,   // Sum of all unit totals at showroom price
  revisionNumber: Int,
  priceListVersion: String,
}
```

### What the CRM Does With It (after BOQ is saved)

When the project status advances (e.g. PIC submits it), the CRM quotation module reads the revision data and generates a quotation automatically. The selling price, discount caps, and any other business rule parameters are configured in the CRM — not in the BOQ tool.

```typescript
async function generateQuotation(projectId: string, discountPct = 0) {
  const revision = await getLatestRevision(projectId);

  const showroomTotal = revision.grandTotal;
  const sellingPrice  = showroomTotal / SELLING_PRICE_DIVISOR;   // CRM-configurable
  const finalPrice    = sellingPrice * (1 - discountPct / 100);

  return await db.stellaQuotation.upsert({
    where: { projectId },
    create: { projectId, boqRevisionId: revision.id, showroomTotal, sellingPrice, discountPct, finalPrice },
    update: { boqRevisionId: revision.id, showroomTotal, sellingPrice, discountPct, finalPrice, status: 'DRAFT' }
  });
}
```

### Document Contents

**Quotation document** (auto-generated by CRM — for Sales team, NOT shown to PIC):
- Header: MULYA / Stella Mobili branding
- Project: name, client, date, PIC
- Units table: room name, item count, selling price per room (not showroom price)
- Grand total at selling price
- Applied discount (if any) and final price after discount
- Terms / validity

**BOQ document** (the tool's own PDF export — for PIC and internal use):
- Same header
- Full itemised table per room: description, finish, handle, qty, unit price, total
- Notes column shown for each item with notes
- Grand total at showroom price
- "Showroom Price · excl. PPN"

## 13. Document Number Format

**The BOQ tool does not generate or assign document numbers.** Document numbers are owned and managed entirely by the MulyaOne CRM.

Format: `BOQ-SM-YY-###-v{n}`
- `SM` = Stella Mobili brand code
- `YY` = 2-digit year (e.g. `26`)
- `###` = 3-digit sequential number per brand per year (e.g. `042`) — assigned by CRM
- `v{n}` = revision number sourced from `StellaBoqRevision.revisionNumber`

Example: `BOQ-SM-26-042-v3`

The document number is auto-generated by the CRM when a project is created and stored in `StellaProject`. The revision suffix updates each time a new revision is saved. The standalone HTML tool has no concept of a document number — it is purely a CRM data field shown on documents produced by the CRM.
